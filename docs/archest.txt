先读一下当前的设计文档和开发计划，再基于已交付的内容做精确的剩余分析。现在对照已交付的代码包做精确盘点，梳理出真正的剩余缺口。好，现在做精确盘点。已交付的代码包里阶段二全部实现了，但原计划里还遗漏了一些产品级必须项，加上还没写进原计划里的工程质量要求。---

把剩余的事情分两类说清楚：

**原计划里还没做的（阶段三/四）** 就是缓存、Tool use、Prometheus、Langfuse、审计日志、A/B 评估、多集群高可用，这些都有详细设计，按顺序推进即可。

**原计划里没有、但产品级必须的** 是三块：

一是**工程质量缺口**。Go 的 `ChatStructured` 目前用 marshal 反推类型来生成 JSON Schema，遇到嵌套 struct 和 slice 会出错，需要换用专门的 schema 库。Python 的 `chat_stream` 是同步 generator，业务如果跑 asyncio 框架会阻塞，需要补 `chat_stream_async`。另外整套 CI 流水线还没有，三语言测试需要在 PR 阶段自动跑。

二是**安全加固**，原计划完全没提。现在所有业务服务共用同一个 `LITELLM_MASTER_KEY`，一旦某个服务的 key 泄露就全线暴露。产品级的做法是给每个业务服务分配独立的 virtual key（LiteLLM 内置了 key management），每个 key 设独立配额和权限，可以单独吊销。配套还需要 K8s NetworkPolicy 限制只有 `apps` namespace 能访问 Proxy，以及把手动 `kubectl create secret` 换成 Sealed Secrets 纳入 GitOps。

三是**包发布配置**还不完整。`pyproject.toml` 缺 classifiers 和正式的 entry_points，TypeScript 的 `package.json` 缺 `exports` 字段（ESM/CJS 双格式），Go module 还没打版本 tag。这些不影响本地使用，但如果要发布到 PyPI / npm / pkg.go.dev 就必须补。

最近的下一步建议先做 CI Pipeline 和 Go schema 升级，这两个是当前代码的质量短板，其他功能建在上面才稳。
